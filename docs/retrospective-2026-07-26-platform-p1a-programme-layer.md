## What was delivered

additive nullable FKs that hang existing data off it (`ScholarshipCohort.programme`,
`ScholarshipApplication.programme`), migrations `0118`/`0119`, and 16 tests. Migrations applied

## What went well

- **Splitting P1 was the right call, and the split line was the right line.** The original sprint
  bundled the structural change with rule-default extraction and routing. Structure is provably
  behaviour-neutral; the other two change what feeds the verification engine and where a live
  applicant lands. Splitting meant this sprint could ship against production the same day, with a
  review small enough to actually read.
- **Mirroring an existing proven pattern cost almost nothing and bought correctness.** The
  application's `programme` copy is the `owning_organisation` pattern applied twice — same
  set-once semantics, same safe-NULL bucket, same drift-guard shape. The test file is deliberately
  a sibling of `test_application_owning_org.py`. Nothing had to be invented.
- **Checking the live database before writing DDL caught two things assumption would have missed** —
  the PK is `bigint GENERATED BY DEFAULT AS IDENTITY` (not a serial), and every sibling table has RLS
  enabled *with* a single `Backend service role only` policy. A hand-written `CREATE TABLE` that
  skipped either would have drifted from the convention silently.
- **The timing was genuinely lucky and we used it.** Production held exactly one cohort with
  `is_open = false`. Introducing the layer against a closed, single-cohort dataset is the cheapest
  this change will ever be, and that was verified by query rather than assumed from memory.

## What to do differently

- **One `save()` derivation now sets two denormalised fields.** It reads cleanly today because both
  come from the same cohort in one query, but a third would make it a pattern in need of a name.
  If P1b or P2 adds another cohort-derived copy, extract a small `_derive_from_cohort()` helper
  rather than growing the conditional.
- **`bursary_e2e.py:142` sets a cohort's organisation but not its programme.** Harmless now
  (nullable column, dev-only command) and deliberately left, but it is exactly the kind of
  half-updated write path that bites once routing reads the column. Logged in the roadmap for P1b —
  the lesson being that the moment a field gains a sibling, *every* writer of the first needs
  checking, not just the production ones.

## Lesson candidates

- **When adding a table to a Supabase-backed project, read a sibling table's RLS state and policy
  set before writing the DDL — not just its column types.** The existing lesson says to mirror types
  via `information_schema`; this sprint showed the same applies to `pg_class.relrowsecurity` and
  `pg_policies`. A new table with RLS off, or on-but-policyless, lands in the security advisor and
  diverges from every neighbour. (Added to `docs/lessons.md`.)
