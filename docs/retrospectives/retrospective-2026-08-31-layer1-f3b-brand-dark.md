# Retrospective — Layer 1 F3b: the brand ramp aligned to dark (2026-08-31)

Branch `feat/layer1-f3b-brand-dark`, stacked on `feat/layer1-f3-student-surfaces`. No migration.
Web only, 4 files. jest 1515 → 1518. Owner direction, same day F3 raised it.

## What Was Built

- **`brandRamp(hex, theme)`** — the derivation now aims at the ground it will sit on. Dark tints
  mix toward the page, dark shades toward white. `500` is untouched in both modes.
- **A dark `--brand-*` block in `globals.css`**, generated by that function rather than typed.
- **`branding-context` recomputes a tenant's ramp on every mode change**, via a `data-theme`
  attribute observer.
- **Four guards replacing one**, stating the owner's ruling as a property rather than a ban.

## What Went Well

- **The fix was findable because F3 refused to guess.** F3 measured the problem (101 uses, 40
  files), wrote down why it could not be fixed without a ruling, and stopped. One sentence of
  direction turned that into a four-file change with no exploration.
- **The right formulation made the ruling and the fix compatible.** "A theme may never write
  `--brand-*`" and "the pale stops must work in dark" look contradictory until you separate the
  IDENTITY stop from the eight derived ones. `500` is the brand; the rest is furniture. Once
  stated that way, the guard got stricter *and* the fix became possible.
- **Deriving rather than picking was forced by the tenant path, and that was lucky.** A hand-picked
  dark palette would have looked fine on BrightPath and been wrong for every tenant. The runtime
  override made the constraint impossible to miss.
- **The inline-style trap was caught by reading, not by testing.** A tenant's ramp is written as
  inline styles on `<html>`, which beat any stylesheet — including the new dark block. Without the
  observer, tenants would have been pinned to the light ramp in dark mode with no CSS remedy.

## What Went Wrong

1. **I wrote two assertions that were wrong about correct code.**
   *What:* the first version asserted "a brand tint is lighter than the page" (in light mode a
   95%-white blue is very slightly *darker* than a `#f9fafb` page) and "the light ramp is generated
   by `brandRamp()`" (it is deliberately the platform's seeded Tailwind hexes — the function's own
   docstring says so).
   *Why:* I wrote the tests from the intent of the change instead of from what the code says. Both
   failed on correct values, which is the cheap direction — but a test that fails on correct code
   is one impatient edit away from being deleted, and then it guards nothing.
   *Fix:* restated against the brand's own `500` as the reference point ("the ends swap"), and the
   generation check scoped to the dark block, with the reason for the light exemption written
   beside it.

2. **`\s` inside a template literal is not `\s`.** The hoisted luminance helper used
   `` new RegExp(`--${name}:\s*([\d ]+);`) ``. In a template literal those are unknown escapes and
   collapse to `s` and `d`, so the regex matched nothing and every assertion threw "no --token".
   Three other copies in the same file had `\\s` and were correct — which is exactly how the
   mistake survives a read-through.
   *System change:* the corrected line carries the explanation, so the next person copying it sees
   why the double backslash is there.

## Design Decisions

- **The identity stop is the ruling.** Recorded in `docs/decisions.md`, superseding the F3 open
  question and re-reading (not overturning) the 2026-07-29 rule.
- **Derived, never picked** — a tenant supplies one colour, so a dark palette has to be a function.
- **The light ramp stays the seeded hexes.** Its byte-identity contract predates the theme work and
  there is nothing to gain from regenerating it.
